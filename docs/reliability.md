# Гарантии доставки и отказы

## At-least-once в обе стороны

Ни одно звено не подтверждает обработку раньше, чем она действительно произошла:

| Звено | Подтверждение | После чего |
|---|---|---|
| бизнес-логика → outbox | коммит транзакции | вместе с изменением сущности |
| outbox → Kafka | `MarkSent` | после ack брокера |
| Kafka → хендлер | `CommitRecords` | после успеха хендлера или записи в DLQ |

Платой за «не потеряем» идут дубли: падение между ack и `MarkSent`, между успехом хендлера и
коммитом, ребаланс посреди батча. **Хендлер обязан быть идемпотентным** — на этом держится все
остальное.

## Матрица отказов

| Что отказало | Что происходит | Потеря | Дубль |
|---|---|---|---|
| БД недоступна при `Fetch` | ретраи `StoreMaxAttempts`, затем заход провален, следующий через `PollInterval` | нет | нет |
| Брокер недоступен при публикации | запись не подтверждена, строка остается неотмеченной | нет | нет |
| Брокер отверг запись окончательно | `MarkFailed`, строка уходит с дороги, в логе `ERROR` | да, осознанно | нет |
| Сервис упал между ack и `MarkSent` | строка приедет в следующем `Fetch` и опубликуется снова | нет | **да** |
| Хендлер вернул преходящую ошибку | ретраи `HandlerMaxAttempts` с бэкоффом | нет | нет |
| Хендлер вернул `ErrPermanent` | DLQ сразу, commit | нет (в DLQ) | нет |
| Ретраи хендлера исчерпаны | DLQ, commit | нет (в DLQ) | нет |
| DLQ недоступна | воркер встает, партиция на паузе, без commit | нет | нет |
| Ребаланс посреди батча | батч брошен, не закоммичен, перечитает новый владелец | нет | **да** |
| Сервис упал после обработки, до коммита | батч перечитается после рестарта | нет | **да** |
| Хендлер завис | `HandlerTimeout` → ошибка → ретраи → DLQ | нет | нет |

## Порядок

Гарантируется **в пределах одной сущности**, и только потому, что ключ записи — `EntityID`: все
события сущности ложатся в одну партицию, а партицию в каждый момент читает ровно один воркер
одного консьюмера группы.

Порядка между разными сущностями нет и не предполагается.

Порядок может нарушиться при ретрае: запись, уехавшая в DLQ, и следующая за ней, обработанная
успешно, приедут в разном порядке относительно исходного. Для ECST это не беда — спасает проверка
версии: применяется только то, что новее.

## Идемпотентность: как именно

**Условный upsert.** Проверка версии и запись должны быть одной операцией:

```sql
INSERT INTO orders (id, sum, version, deleted)
VALUES ($1, $2, $3, false)
ON CONFLICT (id) DO UPDATE
SET sum = EXCLUDED.sum, version = EXCLUDED.version, deleted = false
WHERE orders.version < EXCLUDED.version;
```

Так нельзя:

```go
cur := selectVersion(id)      // ← между этими двумя строками
if cur < e.Version {          //   проедет второй воркер
    update(id, e.Version)
}
```

**`0 rows` — не ошибка.** Это дубль или устаревшее событие. Возвращать `nil`, иначе запись уедет
в DLQ на ровном месте.

**Delete — tombstone.** `deleted = true` + версия, а не `DELETE FROM`: удалив строку, вы потеряете
версию, и старое событие, приехавшее повторно, воскресит запись. Физически чистить tombstone'ы
отдельным джобом по возрасту.

## Что считать `ErrPermanent`

Критерий один: **поможет ли повтор**.

Permanent — битый JSON, конверт без обязательных полей, payload чужой схемы, нарушение
check-констрейнта, отсутствующая внешняя ссылка, которая не появится.

Не permanent — таймаут, deadlock, `connection refused`, `too many connections`, недоступный соседний
сервис, 5xx.

Ошибиться в эту сторону дорого: если объявить сбой БД permanent, весь поток за время недоступности
базы сольется в DLQ, и разбирать потом тысячи сообщений руками. Обратная ошибка дешевле: сообщение
просто полежит лишние несколько секунд в ретраях.

## Чего библиотека не делает

**Нет exactly-once.** Нет Kafka-транзакций между DLQ-записью и коммитом офсета: если консьюмер
упадет точно между ними, сообщение приедет в DLQ дважды. DLQ разбирают руками или идемпотентным
реплеером — это приемлемо.

**Нет автоматического resume паузнутой партиции.** Пауза ставится, когда недоступна DLQ, то есть
когда сломан сам аварийный путь. Автоматически снимать такую паузу нечем — непонятно, по какому
признаку. Снимается рестартом инстанса (при следующем `assigned` партиция резюмится явно).

**Нет реплея из DLQ.** Заголовков `dlq_source_*` достаточно, чтоб написать реплеер под свою
задачу, но готового в библиотеке нет.

**Нет схем-реестра.** `Source.SchemaVer` — просто строка в конверте; совместимость схем на вас.

## Что мониторить

| Сигнал | Смысл |
|---|---|
| `consumer: partition paused` (ERROR) | партиция встала, сама не поедет — **алертить** |
| `consumer: worker stopped` (ERROR) | то же событие со стороны воркера |
| `consumer: record sent to dlq` (WARN) | рост = проблема со схемой или данными |
| `outbox: message failed` (ERROR) | строка уведена в `MarkFailed`, событие не доехало |
| `outbox: record not delivered` (ERROR) | преходящая проблема с брокером; рост = пора смотреть |
| `outbox: mark sent` в ошибке захода | **будут дубли** у потребителя |
| `producer: record delivery failed` (ERROR) | только для `Produce`, где результат не разбирается |
| размер непубликованного хвоста outbox | лаг публикации |
| consumer group lag | лаг обработки |

Логи идут в `slog.Default()` структурированными атрибутами: `topic`, `partition`, `offset`, `id`,
`attempt`, `error`.

## Настройка под нагрузку

**Публикация отстает** — поднять `BatchSize`, снизить `PollInterval`, проверить, что `Fetch` попадает
в частичный индекс. Несколько инстансов разбирают таблицу параллельно при `SKIP LOCKED`.

**Обработка отстает** — поднять `poolSize` топика (но не выше числа партиций), затем число партиций.
Горизонтально — поднять инстансы: партиции разъедутся по группе.

**Группа выпадает в ребаланс** — обработка батча не укладывается в `RebalanceTimeout`. Снижать
`MaxPollRecords`, сокращать `HandlerTimeout`, ускорять хендлер.

**Много мелких событий** — поднять `Linger` продюсера: батчи наполнятся лучше, латентность вырастет
на ту же величину.
